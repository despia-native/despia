# C1: the pure DSX app, four surfaces from one codebase

One project, one set of `.dsx` documents, rendered four ways: native iOS, native Android, an
installable PWA, and a server-rendered site. This is the canonical layout every other
combination is a variation of, and it is the layout `despia-native/despia-example` maintains
as a product.

## The layout

```
my-app/
  dsx.json            # identity: name, scheme, version
  dsx.config.json     # web build: entry component, outDir
  package.json        # @despia-native/* from the registry — never file: paths
  Components/
    App.dsx           # the entry screen
    …                 # every other screen and component
  server/             # optional — <server> documents (C4: the full stack)
  dist/               # generated by `dsx build` (web)
  dist-ota/           # generated by `dsx ota build` (native content updates)
```

Reserved names: see [the contract](../reserved-directories.md). Everything else is yours.

## The walk

```bash
npm create dsx my-app && cd my-app
npm install
dsx dev              # build + serve + live reload
dsx build            # the deployable static site (PWA-ready; SSR via @despia-native/server's site face)
dsx lint --strict    # the same gate CI runs
dsx ota build        # your screens as a content-root folder any static host can serve
dsx export all       # a real Xcode + Android Studio project from this same folder
```

The same `Components/` tree is what the native runtimes render: the iOS and Android kernels
execute the identical documents (the unified-codebase law — one authoring surface, fixtures
first, three renderers). Two ways to an installable app, same sources: the hosted app build
lanes, where signing identities live — or **[`dsx export`](../native-export.md)**, which
writes a complete native project (kernel vendored, your own `Modules/` compiled in) that you
open in Xcode or Android Studio and own outright.

## What CI proves, from tarballs

The matrix gate scaffolds this exact layout through the published `create-dsx` bin, installs
the packed tarballs (never a workspace path), runs `dsx build` and `dsx lint --strict`, and
then runs `dsx ota build` over its `Components/` and verifies every manifest sha — so C1 and
C7 are proven on the same app on every pull request.

## C4 in one sentence

The full stack is this layout plus a `server/` folder of `<server>` documents — routes,
workers, MCP tools — compiled by the emitter and deployed with one command; the recipe is
[writing-a-backend](../../../Skills/writing-a-backend.md).
