JSE semantics corpus — {scope, expression, expected} triples + action-sequence fixtures. Initial ~300 cases are GENERATED by instrumenting the Swift JSE evaluator (W0, /web/10). Do not hand-author what the reference can emit.

## Record mode — the corpus authority

Swift is the reference implementation. The Codemagic **`conformance-record`** lane (manual
trigger — it never runs on a PR) compiles the real open kernel standalone and re-emits every
`*.json` here with `expected` = the Swift kernel's actual result, byte-stable against the
committed files, then **fails on any diff** — the drift alarm. The machinery:

- recorder: `OpenSource/Engine/iOS/JSEConformanceRecord.swift` (compiled only by the lane, never
  by an app target) + `ClosedSource/scripts/conformance/` (shims for the per-app generated
  registries, the `@main` entry, and the driver `record_jse_conformance.sh`).
- Kotlin runs the same corpus on every PR (`Engine/Android ConformanceTest`, android-kernel lane).

Operator flow on an intended JSE change:

1. trigger `conformance-record` on your branch; download the `regenerated/jse/*.json` artifact;
2. commit it over this folder — record mode authoritates `expected`, never hand-edit it against
   the reference;
3. get the Kotlin kernel green on the new corpus: `cd OpenSource/Engine/Android && gradle test`.

An unintended diff is a Swift regression or a bad corpus edit — fix the code, not the fixtures.

Authoring rules (byte-stability): 2-space indent, case keys in `name, scope, expression,
expected` order, scope keys alphabetical (record mode canonicalizes them), integral numbers
written as integers, raw UTF-8, no trailing newline — i.e. exactly what the recorder emits.
