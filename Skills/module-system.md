# Module system architecture

The authoring pattern - a `Module` subclass with `setup()`, the `dsx` API, and the
`JSON([...])` payload literal, written identically in Swift and Kotlin - is branded
**DespiaScript**. Not a new language; the same cross-platform shape for Despia
native extensions. See `writing-a-module.md`.

## Layout

```
DSX/Modules/
  Core/<Module>/dsx.json           # shipped-by-default modules
  Core/<Group>/<Module>/dsx.json   # nest freely for organization (any depth)
  Custom/<Module>/dsx.json         # client-specific modules
  Config/excluded.json                   # committed exclude list
  .plugin_deps.lock.json                 # generated by the build, gitignored (not committed)
Registry/                          # GENERATED output only (*.generated.swift, seeds) — never the engine
```

The engine (kernel) lives in `OpenSource/Engine/`: `iOS/Module.swift` (the `Module`
base class + `ModuleRegistry`), `iOS/Context.swift` (the dsx DSL), `iOS/Bridge.swift`
(`Bridge`/`VirtualBridge`), and the page runtime `runtime.js` (the per-app injected
`custom.js` is the Dom module's declared file, not engine).

`DSX/Modules/` is an Xcode **synchronized root group** - files on disk are the source
of truth; there are no per-file project references to maintain. (`Registry/` is a
synchronized group too — the generated sources there compile by folder membership.)

**Folders nest for organization.** A folder is a module when it directly holds a
`dsx.json` or Swift; a folder with neither (e.g. `Core/Basics`) is just a
group and is recursed into, so a module can live at any depth
(`Core/Basics/StatusBar`) - the grouping folders register nothing themselves. A
`shared` folder is reserved shared code, never a module. The flat layout is
unchanged, and discovery is by folder, so no registration edits are needed.

## Build-time: `ClosedSource/scripts/prepare_modules.rb`

Runs in the Despia CI/CD pipeline before `pod install` (or run it yourself - see
[building.md](building.md)). For the set of *enabled* modules it regenerates,
idempotently:

- the **`Podfile`** managed block (`# === BEGIN/END PLUGIN MANAGED PODS ===`)
- **Swift Package** dependencies on the Runtime target
- the **app `Info.plist`** — GENERATED whole at `DSX/Modules/Mandatory/App/Info.plist`:
  identity skeleton + every enabled module's `infoPlist` (the `App` module
  carries the host-structural keys; no hand-maintained or client plist exists)
- **`Runtime.entitlements`** (merged from each `entitlements`, fanned out to the
  `targets` a module lists)
- **extension targets** (from `extensionTargets`) - synthesized/adopted, and
  torn down when the owning module is disabled
- the **synchronized-group membership exceptions** (a disabled module's source
  files are excepted from compilation one by one - a bare folder path there does
  not drop its `.swift` from the build; `dsx.json`/docs are excepted from
  the bundle)
- **`DespiaPackages.json`** in the app bundle (via `generate_package_registry.rb`,
  an Xcode build phase) - `[{name, version, scheme?}]` for every compiled
  module, surfaced to the page as `window.dsx.packages` (legacy alias: `window.despia.packages`; never Info.plist)
- **orphan `PBXFileReference` cleanup** - any file ref whose resolved path is
  inside the repo but no longer exists on disk gets dropped (with cascading
  `PBXBuildFile` / group-membership removal). Self-heals the project when a
  source file is moved into a synchronized `DSX/Modules/` folder so the old
  WebView/OpenSource group ref doesn't dangle. The `Pods/` tree is skipped
  (CocoaPods materializes those refs after this script runs).

Run it locally after editing manifests:

```
ruby ClosedSource/scripts/prepare_modules.rb
```

It aborts if the `Modules` sync group is missing and warns on collisions /
exclude tokens that match nothing. **Review the `Podfile` + project diff before
committing.**

## Runtime: discovery & dispatch

`ModuleRegistry.bootstrap()` scans the ObjC runtime for every `Module` subclass
(no hardcoded list) and instantiates it. Each module's `setup()` registers its
routes. Incoming `scheme://host?...` URLs (built by `window.despia` from web; the
raw `window.virtual` transport is legacy — see [legacy.md](../Documentation/legacy.md))
are dispatched to the owning module's handler.

-> Adding/removing a code-bearing module needs **no registration edits** - the
class appearing/disappearing is enough.

## Turning a module off

Every module is **ON by default**. Drop one by listing it in the committed
**`DSX/Modules/Config/excluded.json`** - a bare array (or `{"exclude":[...]}`) of
folder name / scheme / alias (case-insensitive, trailing `Plugin` ignored):
```json
{ "exclude": ["microphone", "elevenlabs", "Core/Basics/*"] }
```

To ship a module **off by default**, list it in `excluded.json` and remove it
there per app to enable (this is how Terra and Stream are gated).

Exclusion is **file-presence gating**, not a compile-time switch.
`prepare_modules.rb` removes the excluded module's sources from the Runtime
synced folder; the classes don't exist in that build, their frameworks don't
link, their user scripts don't inject, and their URL schemes fall through to
the host's normal handlers. The host never references a module by symbol, so
there are no `#if FEATURE_ENABLED` blocks anywhere - those couple host code to
specific modules and rot the moment a module moves or is renamed. The
extraction recipe in [extracting-a-module.md](extracting-a-module.md)
enforces this rule.

### Host code that wants to use a module

Three patterns, in order of preference:

1. **Post a `NotificationCenter` event** describing what the host is doing
   (`.downloadStarted`, …). Any loaded module can observe. Excluded
   modules simply don't observe; the post is a no-op. Use this for
   fire-and-forget signals.

2. **Dispatch a URL scheme** via `ModuleRegistry.shared.handle(url:…)`.
   The module's scheme is its explicit public API surface; this is the
   path web callers use too. Returns `false` if no module claims it.

3. **Check availability + run a typed branch**. When the host needs to
   gate work explicitly (e.g. skip building a payload that's only
   meaningful when the module is present), use:

       if ModuleRegistry.shared.isAvailable("liveactivity") {
           // module-specific work
       }
       // surrounding work (cache the file, return the response …)
       // runs unconditionally

   This is the generic answer to "should I run this branch?" - no
   compile-time coupling, no shared-kernel slot named after the module.

In none of these patterns does the host import a module's types or
reference its classes by symbol. Modules are addressed by their
scheme string at runtime.

**Module code wanting to call another module** uses a different surface -
`dsx.module.<scheme>.<action>(args)` (await = result, bare = fire-and-forget) -
which lives on the per-call `dsx` (not available to host code, which has no
`dsx`). See [cross-module-calls.md](cross-module-calls.md).

An entry is a **token** (folder name / scheme / alias) unless it
contains `/` or `*`, in which case it's a **path glob** matched against the
module's path under `DSX/Modules/` - handy for dropping a whole nested group:

- `Core/Basics` or `Core/Basics/*` - every module in that group, at any depth
- `Core/*/StatusBar` - positional; `Core/**/StatusBar` - any depth

When a module is dropped, `prepare_modules` strips **everything** it contributed
- pods, SPM, code, Info.plist keys, entitlements, and any extension target -
leaving zero trace. (Caveat: only what lives *in the module* is stripped; code
still woven into the host app must be removed separately.)
